design · job-hunter · 2026-08-15

One posting shape, eight sources, three markets

Every source normalizes into a single three-ring record — a frozen identity ring, a small normalized core, and a free-form extras ring — and everything interpretive (skills, seniority, scores) lives in a separate relational layer keyed to the exact JD version it came from. The whole database is a cache: it can be deleted and rebuilt from the raw snapshot archive at any time, which is what makes the schema safe to evolve.

01 — ProblemProblem and constraints

Eight source types (Greenhouse, Lever, Ashby, Workable, SmartRecruiters, MyCareersFuture, JSON-LD pages, Yourator) across four markets disagree about everything: field names, timestamp formats, description encoding, salary currency and period, language, and how much structure they offer. The format must be unified enough that one query answers “what changed in my panel this week” across all of them, and flexible enough that a new source never forces a redesign.

Constraints carried from earlier decisions

  • Raw payloads are archived forever and never edited.
  • The store is rebuildable from raw.
  • Changes are events, never overwrites.
  • Fields prefer null over a guess.
  • No scraping of fenced platforms.

Non-goals

  • Merging cross-source identity into one record (duplicates are linked, not merged).
  • Storing derived interpretations inside the posting record.
  • Translating content between languages.

02 — DesignProposed design

A fetch lands as an immutable raw snapshot; a per-source adapter parses it into the unified record; the store diffs against the previous version by content hash and appends events; the derived layer re-computes only for versions whose content actually changed.

03 — RecordThe record: three rings

The rings are layered by rate of change: Ring 1 is a frozen contract the temporal machinery depends on; Ring 2 changes only through a deliberate promotion rule; Ring 3 changes freely per source.

Two hashes split “the employer edited the job” from “the source jiggled its metadata”.

05 — Derived layerThe derived layer: posting → skills → detail

Skills never live inside the posting record.

They are relational rows pinned to the exact JD version they were extracted from, pointing into a canonical dimension whose wording variants collapse in an alias table. Here the three postings above meet: three markets, three wordings, one skill.

Serving is a projection: json_group_array() compiles a per-posting skills digest for the MCP layer on demand, so agents get one convenient array while analytics keeps its indexes — the digest can never drift from the junction because it is derived from it.

06 — DecisionsDecisions and rejected alternatives

Each row is a choice the design turns on, the alternative that was considered, and the reason it lost.

ChosenRejectedWhy
Three rings + promotion ruleOne wide flat table Every new source becomes a migration and a sea of nulls.
Typed core columnsPure JSON documents Discipline erodes; analytics queries degrade to json_each scans.
Two hashes (content / extras)Single hash over everything Source metadata churn would trigger re-embedding and false change events.
Relational skills junctionSkills JSON array per posting Cross-posting aggregation is the point; arrays can't join or index. The array survives as a derived serving projection.
Per-source uid + duplicate linksMerged cross-source identity Merging is an inference; inferences don't get to own identity.
Company = registry keyPayload-supplied names Cross-source joins need one canonical key; payload names become aliases.

07 — FailuresFailure modes

What breaks, what happens when it does, and how it recovers. The common thread is that nothing is ever lost or overwritten, so every recovery is a replay, a filter, or a pointer update.

What breaksWhat happensHow it recovers
Undocumented API drifts (Yourator, MCF) Parse fails loudly, fetch-health flags the source, raw snapshots keep accumulating. Fix the adapter, replay, no data lost.
Salary parse is wrong raw_text is always kept and null-over-guess applies. A bad rule yields nulls to fix, not silent wrong numbers.
Extractor regression New skills rows carry a new extractor_version; old rows are untouched. Comparisons are possible, rollback is a filter.
Normalization rules change hash_version bumps. Re-normalization never masquerades as thousands of employer edits.
Bad skill merge merged_into is a pointer and junction rows were never rewritten. Reversing a merge is an update, not a repair.

08 — TestingTesting strategy

  • Golden fixtures per adapter from the captured payload docs; byte-stable parse output.
  • Rebuild-determinism in CI: replay the raw archive into a fresh store, diff against the incremental one — zero diff or fail.
  • Per-market salary rule tests (万円 annual, monthly TWD/SGD/HKD, ×13–16薪 annualization).
  • Extraction scored against SkillSpan + the in-house gold set; MCF native-vs-extracted agreement monitored as a free accuracy signal.

SummaryThe chain of reasoning

  1. Raw payloads are archived forever and never edited; everything downstream is rebuildable from them.
  2. Every source parses into one three-ring record: Ring 1 frozen, Ring 2 changed only by the promotion rule, Ring 3 free per source.
  3. Two hashes separate an employer edit from source metadata churn, so change events and re-embedding fire only when content changed.
  4. Skills, seniority and scores live in a relational layer pinned to the exact JD version; the per-posting array is a serving projection, never the source of truth.
  5. Because the whole store is a cache, evolving the schema is: add the column, replay the raw archive.
